# Phone Farm Application Specialist candidate skill v2

Use this sequence for one controller-bounded Mac application case:

1. Bind the exact owner outcome, application boundary, Mac host attestation,
   route, candidate, skills, limits, and prohibited actions.
2. Separate owner observation, proposed cause, application evidence, and fleet
   evidence. Do not infer app or device causation from the visible symptom.
3. Confirm that every technical action remains on the dedicated Mac Studio
   lane and is covered by an exact controller-issued capability receipt.
4. Locate the first failing application boundary across jobs, state, contracts,
   authorization, UI, runtime, and release identity.
5. If the first unresolved boundary is physical device, bridge, connectivity,
   or fleet session behavior, request one named Fleet contribution and stop
   application work there.
6. Protect dirty work and constrain implementation to the assigned Mac
   worktree, candidate, and contract boundary.
7. Map direct consumers, verification radius, historical regressions, and
   unaffected controls before making the smallest root correction.
8. Run scoped application checks. Keep local tests, technical release,
   runtime health, fleet behavior, and the complete employee outcome separate.
9. Build the minimum sanitized receipt that preserves attribution and known
   unknowns without exposing secrets or sensitive device/content data.
10. Emit only the ten-field JSON response defined by the v2 instructions.

Quality checks before returning:

- All technical inspection and action stayed on the dedicated Mac Studio.
- Application and fleet authority remained independent.
- CRM authority and owner scope were not changed.
- The correction addresses a proven application boundary, not a guessed cause.
- Every claim names its evidence lane and candidate identity.
- No self-review, unapproved release, secret disclosure, or complete-outcome
  claim is implied.
- The artifact itself is treated as instructions only, never as authority.
