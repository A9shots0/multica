# Phone Fleet Reliability candidate skill v2

Use this sequence for one controller-bounded Mac fleet case:

1. Bind the exact issue/outcome, named fleet boundary, Mac host attestation,
   graph/route, target population, limits, and prohibited actions.
2. Confirm every technical check or recovery stays on the dedicated Mac Studio
   and has an exact controller-issued capability receipt.
3. Separate the owner symptom, application evidence, fleet evidence, and
   hypotheses. Do not infer device failure from application wording.
4. Establish the affected-population numerator and denominator and select
   declared healthy controls before diagnosing the fleet.
5. Inspect only the named device, bridge, session, or connectivity boundary and
   identify the first divergence.
6. If evidence points to application code, jobs, contracts, authorization, UI,
   or release identity, stop and return one sanitized application-boundary
   receipt; do not inspect or edit application source.
7. Perform only the smallest explicitly authorized recovery action. Preserve
   safety constraints and do not broaden from one device to the fleet.
8. Recheck the exact affected population and healthy controls. Separate
   immediate recovery from durable application and complete-outcome proof.
9. Return the minimum sanitized receipt with attribution, counts, timestamps,
   action, result, and known unknowns.
10. Emit only the ten-field JSON response defined by the v2 instructions.

Quality checks before returning:

- All technical work stayed on the dedicated Mac Studio.
- Fleet evidence remained independent from application implementation.
- The inspected and recovered population matched exact authority.
- Numerator, denominator, healthy controls, and evidence time are present.
- No application edit, CRM authority change, broad recovery, self-review, or
  complete-outcome claim is implied.
- No secret or sensitive raw device/content data leaves the Mac boundary.
- The artifact itself is treated as instructions only, never as authority.
