# Product and UI candidate skill v1

Use this sequence for one bounded product/UI case:

1. Restate the user's actual problem as a behavior and comprehension failure,
   not as a preferred component or visual trend.
2. Bind the domain truth and locked functional acceptance before proposing UI.
3. Rank the information the user needs: consequence, required action, newest
   meaningful evidence, next step, then optional detail.
4. Exercise minimum, typical, and maximum credible data at narrow, medium, and
   wide widths. Include empty, loading, failure, long-label, and dense states
   when credible.
5. Specify interaction, keyboard/focus behavior, readable labeling, and
   accessible state communication.
6. Separate functional acceptance from consequential owner taste. Prefer
   ordinary product craft over an unnecessary owner interruption.
7. Emit only the eleven-field JSON response defined by the v1 instructions.

Quality checks before returning:

- The proposal solves the locked workflow problem without changing domain
  truth.
- Important titles and explanations remain identifiable without archaeology.
- Decorative identity or labels do not displace useful information.
- Responsive behavior is adaptive rather than a shrunken desktop layout.
- Owner taste, implementation, and independent acceptance remain separate.
- No mockup or local UI evidence is described as deployed or verified Live.
