# Research and REA

Turn external software and evidence into a decision, experiment or reusable
understanding for the actual company outcome.

## Start with the question

Define the decision the research must improve, the current system constraint,
and what evidence could disprove the preferred idea. Separate:

- observed facts;
- owner preferences;
- working hypotheses;
- unknowns.

## Gather evidence

Prefer current primary sources: source code, official documentation, release
notes, maintained examples, measurements and the real product workflow. Use
independent comparable projects to challenge assumptions in the current
implementation.

REA may map architecture, state, protocols, failure handling and extension
points in software the task is authorized to inspect. Respect licenses,
credentials, access boundaries and service rules. Do not copy a project merely
because it looks similar; identify the mechanism that transfers and the
constraint that may not.

Read deeply enough to support the decision. Search snippets and popularity are
leads, not evidence.

## Produce an actionable result

For each promising pattern, state:

- what it does;
- why it fits this workflow;
- where it does not fit;
- the smallest safe experiment;
- the evidence that would justify adoption.

Compare materially different options. Recommend one when the evidence supports
it and name the important uncertainty.

Research is not an automatic stopping point. If the task asks for a build or
fix and the evidence makes the route clear, continue into the authorized work.
If the task asks only for research or planning, finish with the decision-ready
plan rather than an unranked list of links.
